04 等価性検証

合成後のネットリストが、RTLと論理的に等価であることを証明する。

はじめに: 等価性検証とは

論理合成ツールは、回路を書き換えて最適化します。もしその過程で機能が変わってしまったら、後の工程で見つけるのはとても大変です。

等価性検証は、書き換え前（RTL）と書き換え後（ネットリスト）がどんな入力でも同じ出力を返すことを、数学的に確認します。シミュレーションが「入れた例では合っていた」ことしか言えないのに対し、「全部の場合で合っている」と言えるのが違いです。

実行方法

いちばん簡単make fm（リポジトリの最上位で実行）
直接実行cd fm; fm_shell -f fm.tcl >& fm_run.log
入力rtl/*.v、dc/MAC4.net.v、dc/MAC4.svf（合成ツールの最適化の記録）
出力fm/fm_run.log、unmatched.log、failing.log、passing.log
成功の確認grep "FORMALITY RESULT" fm/fm_run.log → FORMALITY RESULT: PASS
  • 先に make syn が済んでいる必要があります。
  • FAIL のときは failing.log に、等価でなかった場所が出ます。

シミュレーションは「テストした入力では正しい」ことしか示せません。等価性検証 (Formal Equivalence) は、RTL とネットリストの すべての入力 に対して出力が一致することを数学的に確認します。

ツールは Synopsys Formality（fm_shell）です。

流れ

  1. set_svf: 合成ツールが行った最適化のヒントを渡す（これがないと、状態の並べ替えなどで失敗しやすい）。
  2. reference = RTL、implementation = ネットリスト（セルの機能はライブラリから読む）。
  3. match: 両者のレジスタ・ポートを対応づける（比較点を作る）。
  4. verify: 比較点ごとに組み合わせ論理が等価か証明する。

失敗したら

  • unmatched.log: 対応づけできなかった点。名前の変化・定数化されたレジスタが典型。
  • failing.log: 等価でなかった点。ここに出たら本当に論理が変わっています（合成のバグ、または RTL のシミュレーションと合成の解釈の違い）。
いつ使う？
合成後と、配置配線後の両方で行うのが標準です。物理実装の途中でツールが論理を触る（バッファ挿入・ゲートの置換など）ためです。

演習

  1. RTL の acc + a_q*b_q を一時的に変えて、RTL だけ変更し make fm を実行（ネットリストは古いまま）。FAIL の出力を読む。
